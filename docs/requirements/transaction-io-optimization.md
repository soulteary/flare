## 实现边界与安全理由

优化只合并同一请求内的重复安全事务。入口使用已持久化的高水位、当前撤销表和代际生成暂定身份，不采样新的安全墙钟，也不取得发送响应的权限。只允许明确列出的、完全缓冲且无外部副作用的 GET/HEAD：`/applications`、`/bookmarks`，以及离线模式 `/` 的首页和本地搜索。在线首页可能触发天气访问，保留原来的持久化入口检查；写入、导出、近期重认证及其他路由均不进入这条路径。

响应发送前，所有结果均经过最终新鲜持久化会话检查，包含成功、错误状态、返回 error、取消、超时、panic 和误注册流式输出。撤销则清除准备好的私有响应并拒绝；状态故障则闭锁；流式响应在这条路径上拒绝。只有成功前台 GET 延长空闲时间，HEAD 和失败结果不延长。暂定身份期间内容加载严格禁止初始化 YAML，已有配置和缺失文件不会因尚未完成授权的读取被创建或修复。

不采用响应先返回的定时高水位刷新或异步刷盘：这些方案会在响应释放后留下未持久化的安全时间窗口，使崩溃恢复、时钟回退、撤销和故障传播语义改变。同步 group commit 若所有响应均等待持久化完成且撤销排序正确，原则上可能安全，但需要额外排队、一致性协议及延迟预算，本轮未实现。本方案仍在每个请求释放响应前完成一次完整事务，剩余的 journal、state、文件同步和目录同步承担恢复与持久性边界，不能为了更低计数直接移除。

## 完整 HTTP I/O 计数

诊断二进制与原生性能二进制分开构建。优化前诊断来源为 `e5e30c8` 的 Git archive；优化后来源为最终冻结的实际工作区。`transaction_overlay.py` 只改写临时副本，覆盖 Store 的 commit 入口、atomicWrite 入口和四处 `os.File.Sync` 调用点，计数端口只属于既有 test-only localhost wrapper；生产构建没有计数接口。计数器在每条完整 HTTP 请求前后取差，不包含启动和其他并发请求。

每版均验证 24 个认证/匿名 GET/HEAD 请求，覆盖首页、搜索、应用、书签、分类和不存在的分类；另验证登录、CSRF 退出与旧 Cookie 重放。所有状态、HEAD 空响应及实际私有卡片断言通过。成功认证读取由 **2 次 commit、4 次 atomicWrite、4 次文件 Sync +6 次目录 Sync**，减为 **1 次 commit、2 次 atomicWrite、2 次文件 Sync +3 次目录 Sync**，均减少 50%。不存在分类的认证 404 仍为一次事务；匿名读取均零事务。登录一事务、退出两事务、撤销后重放零事务，前后不变；全部 Sync 错误计数为零。

这里的 Sync 是实际调用 Go `os.File.Sync` 的次数，范围仅 `internal/security/store.go`，不是内核系统调用追踪，也不包含内容 YAML 的持久化。单次剩余事务仍为 journal/state 两次原子写入和五次 Sync 调用。额外 Stat 和原子计数会干扰性能，因此这些诊断二进制不参与原生 CPU/RSS 计时。

原始 [优化前计数](../../metrics-reports/transaction-io-optimization-2026-10-27/http-counts-before.json)、[优化后计数](../../metrics-reports/transaction-io-optimization-2026-10-27/http-counts-after.json) 与两份 overlay manifest 保留了每个请求的完整计数、状态、长度和摘要。全部响应长度一致；首页/搜索完整 HTML 摘要包含动态展示内容，不以摘要相等替代卡片授权断言。

## 四轮三分钟结果

全部原生正式测量在其他 agent 停止构建、测试和诊断的空闲窗口顺序执行。固定速率优化前为 UTC 03:51:18–03:54:18，优化后 04:07:58–04:10:58；饱和优化前 03:54:40–03:57:40，优化后 04:11:38–04:14:38。北京时间均加八小时。各轮实际单调时长不少于 180 秒。

固定 3 请求/秒的两版均完整接纳并完成 **540 次读取、90 次安全探针**，零丢弃、零操作异常、零私有内容断言失败。两版均为首页/搜索各 270 次 HTTP 200；首页响应总量均 729,236,520 字节，搜索均 10,188,450 字节，输入夹具及输出长度一致。安全探针全部通过登录、私有读取、CSRF 退出和撤销 Cookie 重放检查。

- 首页 p50/p95：70.43/134.82→47.94/114.53 毫秒。
- 搜索 p50/p95：54.16/64.03→31.74/46.73 毫秒。
- 进程 CPU 累计 12.14→11.75 秒，每完成读取的固定混合负载 CPU 成本 22.48→21.76 毫秒，下降 **3.21%**。分子包含相同的 90 次安全探针及管理员准备登录，不能称为纯 GET 的精确成本。
- 内核 RSS 高水位 139.08→143.05 MiB，增加 **2.85%**。本轮没有证明内存改善，也没有依据这个小差异定位内存回退。

四并发饱和读取优化前完成 3,268 次、优化后 6,623 次，全部 HTTP 200：

- 总吞吐 **18.15→36.77 次/秒，增加 102.66%**。
- 首页 p50/p95：221.13/420.28→137.17/196.58 毫秒；搜索 175.57/321.80→63.99/137.36 毫秒。
- 内核 RSS 高水位 181.48→178.84 MiB，下降 1.46%，属于本轮小差异，不作为内存优化主张。
- 安全探针分别 61 次和 72 次，全部登录 HTTP 303 且授权/撤销断言通过。探针是完整探针结束后再等待两秒的既有闭环 worker；优化后执行更快，所以数量不同。饱和结果表示同样四个读取 worker 和同样探针机制下的完成能力，不是严格相同混合完成量；等成本结论以固定速率的 540+90 配对为准。

所有四轮均满足事前首页 p95 <3 秒、搜索 p95 <1 秒、RSS <1 GiB；全部读取和安全探针无错误或隐私失败。完整机器判定为 [verdict.json](../../metrics-reports/transaction-io-optimization-2026-10-27/verdict.json) 的 `all_gates_pass: true`。事务和 Sync 调用次数减半由独立 HTTP instrumentation 直接观察；吞吐和延迟结果支持该方案在此场景的实际收益，但没有逐请求阻塞时间追踪，不能把每个收益百分比唯一归因于 Sync。

这是每种模式各一对 180 秒样本，没有置信区间或统计显著性检验。固定负载 CPU/RSS 差异较小，核心结论是成功认证读取的事务与同步调用减半，以及本机四并发下的吞吐和延迟改善；不外推到 NAS、低端 ARM、容器限额或物理断电行为。此前 30 分钟登录压测仍是独立历史记录，本轮三分钟不替代该持续性证据。

# PR #214：免登录首页与只读搜索的 CSRF 开销对照

本报告只评价 [PR #214](https://github.com/soulteary/flare/pull/214) 的变更，不比较发布版本。优化前为 `7e91e8f9ed066cafd5f4c088002aa93e4354be90`，优化后为 `12ff92842acccd9be6de197037831a11243e30e4`。两者生产代码仅改变首页渲染时生成 CSRF 的条件；测试和文档不参与运行时负载。PR 已合并，本报告作为后续测量记录补充。

## 如何解读这次优化

- **确定消除的工作**：全部窗口的阶段前后检查中，首页、GET/POST 搜索响应的 `Set-Cookie` 数量均从 1 变为 0，HTML 减少 87 字节。去掉整个 CSRF 隐藏字段后，两版页面在全部配对与轮次中完全一致。正文脱敏不改变长度。
- **大页面首页的收益最一致**：1,000 个书签时，6 对实验的吞吐都上升，配对变化中位数为 **+43.0%**；闭环 CPU/请求 **−31.1%**。固定 40 请求/秒时，CPU/请求 **−34.0%**、P95 **−27.8%**，各对方向也一致。这是本环境的实测结果，不应只归因于 HMAC 函数本身或承诺生产中同样幅度。
- **搜索收益较小，且有波动**：20 个书签的 GET 搜索，6 对吞吐均上升、闭环 CPU/请求均下降，中位数为 **+9.8% / −8.8%**。其他搜索组和小页面首页虽多项中位数改善，但部分配对反向；不能概括为“所有页面都稳定提升”。1,000 书签的 POST 搜索固定流量 P95 中位配对变化反而为 **+4.3%**，不宣称其延迟改善。
- **内存不是普遍性大幅下降**：大页面首页闭环 RSS 中位数从 **42.60 降至 40.31 MiB**，每窗采样峰值的中位数从 **49.95 降至 46.37 MiB**；其余主要场景的闭环 RSS 中位数变化均不到 0.3 MiB，且有小幅上升。这里没有测每请求分配或长期存活堆，不将结果描述为无泄漏或长期内存保证。
- **不保存 Cookie 的结果单独看**：这组仅 4 对，波动和调度迟到更大。POST 搜索吞吐与 CPU 的配对方向一致改善，首页则有反向配对；不能用这组更高的部分百分比替代浏览器复用 Cookie 的主要结果。

## 结果

共 88 个正式窗口、7,803,076 个测量请求；另有每窗口 200 个预热请求，不计入性能统计。每个请求检查状态与正文长度，按每 256 个请求抽查完整正文，并校验阶段前后响应。

固定速率阶段共丢弃 64 个调度请求，涉及 3 个窗口；逐轮调度 P95 最大值 16.792 ms。主要场景丢弃 3/43,200 个计划请求；不保存 Cookie 的补充组丢弃 61/16,000 个计划请求。丢弃不计为已完成请求，也不被隐藏。

## 测量设计

- Linux ARM64 容器运行于同一虚拟机：5 个逻辑 CPU、约 5.35 GiB 内存、cgroup v2。服务端与客户端各设 `GOMAXPROCS=2`；没有 CPU 绑核或容器资源上限。虚拟机还运行其他容器，因此存在系统噪声，结果不能直接当作独占物理机容量。
- 两版同用 Go 1.27.3、`CGO_ENABLED=0`、`GOOS=linux`、`GOARCH=arm64`、`-trimpath -buildvcs=false`，先生成资源再编译。公共基础镜像固定到摘要；版本与二进制摘要见 [builds.json](builds.json)。
- 启用免登录、离线模式及搜索框；访问日志使用当前默认的 `errors` 策略，只记录失败请求，容器日志驱动关闭；使用合成数据，关闭天气与时钟显示。分别放置 20 / 1,000 个书签、8 个应用和 4 个书签分类。搜索最后一个书签，只命中 1 条；不加载浏览器子资源。
- 首页：`GET /`；只读搜索：`GET /?search=000019`、`POST /`（表单 `search=000019`）。大数据集对应 `000999`。不发送管理写请求，不测登录、TLS、代理或公网网络。
- 主要场景启用 Cookie jar，模拟重复访问时保存并复用 Cookie。每个场景 6 对实验，按 AB、BA 交替，前后版本各占首位 3 次。补充场景关闭 Cookie jar，仅测小数据集首页和 POST 搜索，各 4 对；这些数据不与主场景混合。
- 每个版本/场景/轮次启动全新服务进程，固定预热 200 请求，等待 250 ms。随后先测 5 秒固定到达率（小数据集 200 请求/秒，大数据集 40 请求/秒），再测 5 秒闭环负载。并发上限和连接池均为 8，复用 HTTP 连接，禁用压缩。固定到达阶段记录调度迟到和丢弃，保留全部正式轮次；闭环阶段不做 coordinated-omission 修正。
- 客户端位于独立容器/cgroup，共享服务端网络和 PID 命名空间。服务端 CPU 取目标 cgroup 的 `usage_usec` 差值，除以完成请求数得到 CPU 微秒/请求；除以阶段时长得到平均占用核数。该值包括服务端后台工作，不包括独立客户端 CPU。原始数据同时保存客户端 CPU 供排查瓶颈。
- 内存使用目标进程 `/proc/1/status` 的 RSS，每 50 ms 采样，汇总每阶段样本中位数、采样峰值，并保留 `VmHWM`。HWM 包括启动、预热和此前阶段；RSS 不是 Go 活跃堆、分配字节/请求或内存泄漏指标。cgroup 内存另存，包含缓存，不能替代 RSS。
- 每个阶段保存请求数、错误、延迟分位数、CPU、RSS；每 256 个请求校验完整页面，阶段前后另取完整响应。跨版比较去掉整个 CSRF 隐藏字段后的页面字节和导航投影；只允许这个预期差异。

## 统计口径与限制

表内前后值是各轮统计量的中位数；变化是每对 `(after / before - 1) × 100%` 的中位数，括号为所有配对变化的最小值和最大值，是观察范围，不是置信区间。两种“中位数”计算顺序不同，所以百分比可能不等于表内中位数直接相除。吞吐包括客户端 Cookie 解析和保存成本，不能把全部变化归因于服务端 Token 计算。QPS 越高越好，延迟、CPU/请求越低越好；内存必须结合波动解释。延迟分位数按排序后 `floor(N × p)` 的零基索引取值，并限制在最后一个样本以内；不插值。延迟是客户端 HTTP 往返时间，从实际发起请求计时，不包含调度等待；调度迟到另行保存。它不是纯服务端处理时间。

固定到达率阶段用于同流量比较延迟与 CPU。闭环阶段用于比较这个客户端与环境下的吞吐上限，其延迟是在各自不同的饱和负载下得到，不能据此推断同流量延迟。5 秒窗口与有限重复次数不支持生产 SLO、长尾概率、长期内存增长或普适性能保证。特别是大数据集固定到达率每轮仅 200 请求，P99 主要由少量最慢样本决定。

配置校准期间修正了两个采集问题：旧脚本的全量访问日志改为当前默认 `errors`；“遇到调度丢弃即停止”改为保留并报告丢弃。完成校准后从头采集完整实验；此前预演不计入正式结果，正式轮次不按性能筛选。

AB/BA 是固定交替顺序，不是随机试验；即使各对方向一致，也不等于已经做过统计显著性检验。在共享虚拟机上，调度、频率和 GC 状态均可能引起波动；配对范围若跨过零，不声称逐轮一致提升。没有 CPU profile 或堆分配测量，不将端到端差异全部定量归因于某个内部函数。

## 数据与复现

[summary.json](summary.json) 保存各场景汇总和逐对变化，[windows.csv](windows.csv) 保存逐轮指标，[raw.tar.gz](raw.tar.gz) 保存 88 个完整测量记录。[analyze.py](analyze.py) 从窗口记录重算汇总与 CSV，并验证请求计数、吞吐公式、正文、Cookie 行为和轮次数；[privacy.py](privacy.py) 递归检查文件和归档元数据。

归档没有逐请求延迟序列。P50/P95/P99 由采集器按已公开算法在线计算；离线校验能验证分位数顺序及其跨轮汇总，但不能独立重建原始延迟分布。CPU/请求、吞吐和 RSS 汇总则可以由归档中的计数与采样重算。

复现需要 Git、Go 1.27.3、Python 3.12+ 及兼容 Docker 命令的 ARM64 Linux 容器环境。运行时环境及其他负载应另行记录，不能期待相同绝对数值。克隆仓库后在仓库根目录执行；工作与输出目录应为空，复测已有实验时应另选新目录：

```sh
REPORT=metrics-reports/trusted-readonly-csrf-2026-10-27
mkdir -p .benchmark/csrf-capture .benchmark/csrf-work .benchmark/csrf-output
for name in build fixtures compare; do
  cp "$REPORT/capture/$name.py.txt" ".benchmark/csrf-capture/$name.py"
done
cp "$REPORT/capture/runner.go.txt" .benchmark/csrf-capture/runner.go
export FLARE_BENCH_ROOT="$PWD/.benchmark/csrf-work"
export FLARE_BENCH_OUTPUT="$PWD/.benchmark/csrf-output"
python3 .benchmark/csrf-capture/build.py
python3 .benchmark/csrf-capture/fixtures.py
python3 .benchmark/csrf-capture/compare.py
cp "$REPORT/analyze.py" "$FLARE_BENCH_OUTPUT/analyze.py"
python3 "$FLARE_BENCH_OUTPUT/analyze.py" "$FLARE_BENCH_OUTPUT/windows"
# 验证已保存的本次数据，不重新测量：
python3 "$REPORT/analyze.py"
python3 "$REPORT/render.py" --check
python3 "$REPORT/test_integrity.py"
python3 "$REPORT/privacy.py"
```

复现脚本会使用 `flare-csrf-server`、`flare-csrf-observer` 两个临时容器名，并在每个窗口前后清理这两个容器；请勿将其用于其他服务。镜像以 `flare-csrf-bench:*` 命名。随机管理密码仅在启动命令内使用，不写入测量记录。

发布数据只使用合成链接和名称；不保存本机绝对路径、主机名、容器标识或真实配置。响应 Cookie 只保留数量，隐藏 Token 等长替换为 `X`，相应正文 SHA-256 基于脱敏字节重算，原始字节长度保留；采样正文仅保存归一化摘要。归档移除用户、组、精确时间和文件路径前缀，数值测量不改写。

## 验证

[validation.json](validation.json) 记录检查结果：资源生成、原生构建、全量 `go test -race -count=1`（全包插桩覆盖率 91.2%）、`go vet`、golangci-lint 2.15.0 均通过。被检查的合并提交与优化后提交的源码树相同。本次仅新增报告及性能索引，不修改生产代码。

从发布的构建脚本另行重建，两版应用、采集器二进制及两组夹具的 SHA-256 均与实测版本一致。88 个窗口的响应、计数、摘要重算与隐私扫描通过。归档及可见文件不包含个人本地路径、主机名、容器标识、真实 Cookie/Token 或精确采集时间。

校验链同时检查逐轮 CSV 与报告生成区，`render.py --check` 只验证不改写。调度丢弃数按原始数据生成，不使用手填常量。[篡改检测测试](test_integrity.py) 覆盖被修改的 CSV、汇总、吞吐、正文抽样计数和报告单元格，并验证丢弃计数随输入数据更新。

# Flare 0.4.0 / 0.5.0 / 0.6.9 受控性能比较

测量日期：2026-10-27。本报告固定比较 0.4.0、0.5.0 和 0.6.9，不代表后续主分支的性能。

[离线交互图表](index.html) · [复核与重放说明](README.md) · [汇总数据](summary.json)

## 如何使用结论

这是三个版本源码在同一工具链和 Linux ARM64 环境下的受控比较。它回答在这些相同工作负载下的版本差异，不是原始发行包、框架单变量、所有部署硬件或浏览器整页性能的排名。

本次场景中，0.5.0 与 0.4.0 的性能总体接近；0.6.9 明显减少请求计算成本。以下首页吞吐比采用同轮配对比值的六轮中位数，后文同时保留各版本指标中位数。

- 20 条书签首页：0.5.0 / 0.4.0 吞吐比 1.01；0.6.9 / 0.4.0 吞吐比 **5.56**。首页 p95 从 2.844 降至 0.644 ms；CPU/请求从 311.83 降至 53.41 µs。
- 1000 条书签首页：0.5.0 / 0.4.0 吞吐比 1.01；0.6.9 / 0.4.0 吞吐比 **33.86**。首页 p95 从 80.842 降至 3.104 ms；CPU/请求从 10139.94 降至 276.60 µs。

## 冻结对象与构建

- 0.4.0：`9d209e38a3bc7637e14e0762efc7e4bc8f39d03e`；二进制 SHA-256 `23ed448d1b231d03ac2df7b4d30f54ff71aa15e1addd494ab1913968f25001f6`；未裁剪二进制 23.84 MiB。
- 0.5.0：`939551f662c12d0067c6952cc7dc036fa713a506`；二进制 SHA-256 `223066c8782d0f7f9d24d193e9fdc70692678b1489937222a9cc952c8a307333`；未裁剪二进制 24.62 MiB。
- 0.6.9：`9e8b34ba1bfa7f2ec0ca153d82f9fa5ce14897ea`；二进制 SHA-256 `a0234226bc2fd1aa57ea5f3f170c1b821080b547e67b154815e42ae221fc31c3`；未裁剪二进制 29.27 MiB。

- 全部执行各自版本的 `go run build/build.go` 生成资源，再使用 Go 1.27.3，`GOOS=linux GOARCH=arm64 CGO_ENABLED=0 go build -trimpath -buildvcs=false`。没有修改服务端源代码，未增加 profiler，也未关闭新版的安全逻辑。
- 依赖保持各版本原样：统一编译器并不统一版本依赖，依赖升级属于被测版本变化。
- 三个新建测试镜像共用同一 `arm64v8/alpine:3.16` 基础镜像；固定提交、二进制摘要及去除本机路径的 Go build info 见 builds.json。这些是受控构建，不冒称历史发布包。

## 环境与方法

- Linux ARM64 Podman VM：5 个可见 CPU、约 5.35 GiB 内存。服务与独立客户端均 GOMAXPROCS=2，未绑核、未加 CPU/内存配额。后台负载未隔离，无法彻底排除其影响。
- 目标容器 network=none，客户端加入目标的网络和 PID namespace，HTTP 走容器内 127.0.0.1，避免 macOS/VM 端口转发路径。客户端使用独立 cgroup；不共享服务端 CPU/内存计数。
- 全部关闭登录、天气和时钟，使用同一配置和 YAML；每个数据集固定 8 个应用、20 或 1,000 条书签、4 类，唯一静态 URL。所有场景启用正常生产路由。
- 新版设 FLARE_ACCESS_LOG=all，旧版保持原生请求日志；全部使用相同 none 容器日志驱动。日志格式/次数仍随实现变化，成本保留。没有使用 FLARE_BASELINE。
- 每个版本/场景/轮次启动全新容器，先请求验证，再顺序预热 1 秒；文件留在相同 overlay 文件系统中，没有主机目录挂载。
- 六轮使用全部六种版本排列，每个版本恰好两次处于每个执行位置。先完整测试 20 条，再完整测试 1,000 条；两种规模之间不做逐时配对归因。
- 闭环负载：8 个 worker、8 个连接，每窗口 5 秒，截止后等待在途完成，统计实际墙钟时间。是该客户端与资源条件下的完成速率，不直接等于生产最大 QPS。
- 同到达率首页：20 条数据用 40 次/秒，1,000 条用 10 次/秒，窗口 5 秒；无等待队列，8 个在途槽位。分别应完成 200 与 50 次请求。随后在同一目标进程运行闭环负载；这是固定顺序。
- 请求显式 Accept-Encoding: identity，不跟随重定向；客户端没有 CookieJar，不跨请求回放 Cookie，是无状态匿名 HTTP 客户端。新版每次生成 CSRF 的实际成本被保留。这不模拟完整浏览器会话，也不测 gzip、TLS、DNS、远程网络、浏览器资源下载与布局。
- CPU：服务容器 cpu.stat usage_usec 的差值/完成量，含 GC 与日志，不含客户端。另记录客户端 cpu.stat 验证工具开销。
- RSS：/proc/1/status，每 50ms 采样；另保留该进程 VmHWM 和 cgroup memory.current。RSS 不是 Go 堆或分配字节；本次没有服务端 allocations/op 指标。
- p50/p95/p99 从单窗口响应完成延迟排序后取 floor(n×p) 索引（0-based）；不包含固定速率请求计划时刻至发出的等待，后者单独记录为 ScheduleLag。报告数字均为六个窗口指标的中位数，不是合并请求后的百分位数。

## 正确性校验

完成 144 个正式窗口、8,871,300 次计时请求（含固定到达率）。全量检查状态、完整正文长度及跳转 Location；每 256 次采样完整正文哈希；每窗口首尾保存脱敏响应并检查归一化后正文一致。

唯一归一化是新版 HTML 隐藏字段 csrf-token 的随机 value；公开正文中的 CSRF 值以等长占位符替换，Cookie 和精确时间已移除；Hash 对应脱敏后的正文，NormalizedHash 仍使用原有规范化规则。试跑与调试窗口不进入统计；正式窗口使用相同的校验规则。

全部窗口还核对有序导航 URL、文字、target、rel：同场景三版一致。搜索只返回最后一条书签；跳转必须指向其唯一 URL，旧版 /redir/<base64> 与新版 /redir/url?go=<base64> 分别适配。不会把错误页、首条应用命中或少输出内容算成快。

同一版本首尾响应检查不等于跨版本所有 DOM/CSS/JS/图标完全相同。新版 HTML 和 CSP 确实不同，不能由服务端延迟推导浏览器视觉完成时间。

## 相同到达率：首页

- 20 条，40 次/秒：p95 3.548 → 3.455 → 2.119 ms；CPU 1,815.73 → 1,845.47 → 841.32 µs/请求；采样峰值 RSS 20.15 → 21.47 → 23.02 MiB。六轮计划发出和完成量均符合预期，零在途丢弃。
- 1000 条，10 次/秒：p95 27.563 → 28.125 → 3.961 ms；CPU 27,558.31 → 28,120.06 → 2,237.74 µs/请求；采样峰值 RSS 25.36 → 27.31 → 29.35 MiB。六轮计划发出和完成量均符合预期，零在途丢弃。

这组低到达率结果用于观察较轻负载下的成本；发送速率被人为固定，不能把完成速率称为吞吐提升。ScheduleLag 与客户端 CPU 的逐轮数据见 summary.json / 原始窗口。

## 页面体积与内存成本

- 首页未压缩 HTML：20 条书签为 19,903 / 19,902 / 45,134 字节，1,000 条为 228,643 / 228,642 / 319,534 字节（依次为三个版本）。服务端响应更快不代表网络传输或浏览器渲染同幅改善。
- 相同低到达率下，0.6.9 的首页 RSS 高于 0.4.0：小数据约多 2.87 MiB，大数据约多 3.99 MiB；在大数据闭环负载下，0.6.9 的 RSS 峰值反而更低。两种负载不能混用。
- 同工具链未裁剪二进制从 23.84 MiB 增至 29.27 MiB；这不是容器压缩下载量或运行时 RSS。

## 统计口径与不确定性

报告同时保留各轮原值、指标中位数、逐轮配对比值及范围。summary.json 的 bootstrap95 使用固定种子 20261027，对六个配对比值重采样 10,000 次，给出中位比值的百分位区间。六轮样本仍很少，这只是这批窗口的重采样不确定性，不覆盖主机、温度、后台服务、数据分布和部署差异；不把小幅差异解释为普遍性能改进或回归。

## 原因与边界

- 0.4.0 和 0.5.0 均在读取后反复 YAML 解码，并使用大量字符串拼接；0.5.0 更新 Gin、日志，并加入逐项动态 URL 替换。只读代码可说明成本路径变化，不能单独证明某一行或框架造成了本次百分比。
- 0.6.9 缓存解析后的快照和导航 HTML，减少重复解码和渲染。该版本已有 HTML 片段缓存；本报告不包含之后 HEAD 的搜索/分类只读优化。
- 0.6.9 HTML 缓存上限为 16 MiB、64 项、单项 1 MiB；搜索、选中分类、编码链接及动态链接会绕过。当前数据集的无搜索静态导航可命中，不能外推到更大页面和动态内容。
- 跳转选择最后一条书签，用于覆盖旧版完整查找；首条应用命中会有不同的收益比，不能把本场景推广为所有跳转。
- 固定到达率阶段前仍使用同样 1 秒预热，但各版预热完成请求数不同，RSS 可能保留不同的堆/池状态。没有强制 GC 或冷却清空，因此不能将固定到达率 RSS 全部归因于缓存，也不是长期空闲常驻内存。
- 本次不测真实持久化登录会话；0.6.9 的认证语义与旧版不同，不能假设已登录请求有同样速度倍数。
- 本次没有冷启动、清空系统页缓存、长时间内存稳定性、完整浏览器体验或 NAS/小核设备测量。未测维度不下结论。

## 复核入口

完整窗口保存在 `raw-windows.tar.gz`，归档内为 `windows/`。归档的每个文件均已与打包前 SHA-256 比较一致，清单为 `raw-manifest.json`。运行 `python3 verify.py` 可在临时目录检查归档并重算全部统计，不改写记录；完整重放方法见 [README](README.md)。

- `builds.json`：冻结提交、二进制/镜像摘要、完整 Go build info。
- `environment.json`：环境、参数和客户端摘要。
- `summary.json`：中位数、六轮值、配对范围与 bootstrap 区间。
- `windows/*.json`：所有正式窗口、阶段 CPU/内存快照、调度延迟、错误计数、脱敏响应与导航投影。
- `windows/*-Pre.html` / `*-Post.html`：脱敏首尾响应；CSRF 使用等长占位符。
- `fixtures-20/`、`fixtures-1000/`：实际输入配置。
- `capture/`：脱敏脚本快照；`replay.py` 在新目录中适配路径和唯一容器名称重放；`verify.py` 离线复核；`render.py` 从汇总生成图表。

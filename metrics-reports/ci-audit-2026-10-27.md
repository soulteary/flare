## 所有 workflow 的耗时与处理建议

### 1. CI：6 个并行 job

样本 A 合计 230 秒：格式 13、vet 47、lint 51、测试覆盖率 107、容器发布校验 6、GoReleaser 配置检查 6。样本 B/C 合计分别 246/226 秒。

- **格式检查**：gofmt 本身 0 秒，setup-go 8 秒。格式 job 不下载依赖、不编译，却参与共享 Go 缓存写入。立即设置 `cache: false`。可将格式检查放入 lint job 前面，省一次 checkout/toolchain；但合并 job 会改变 required check 名称，需要同步分支保护。
- **vet 与 lint**：独立 vet 32 秒左右，golangci-lint 已启用 govet（配置还排除了 build/ 内部分告警），`go test` 默认也执行部分 vet 检查。存在明显重叠，但不能直接认定完全等价；对比实际分析器、测试文件和 build/ 排除范围后，优先在 lint 中统一补齐，再删除独立 job。仅迁移命令而串行执行，可能减少机器用量却增加 lint 等待时间。
- **测试**：PR 使用 GTR 62 秒，质量报告 6 秒；main 使用原生 race+coverage 77 秒。两者由 if 互斥，**当前同一 job 没有执行两遍全量测试**。继续保留 race、`-count=1`、全包 `-coverpkg=./...` 与 85% 门槛。
- **报告包装成本**：GTR 内部先设置 Action 自身 Go 1.27.2，再设置项目 1.27.3；GoReportCard 又设置自身 1.27.2，所以末尾恢复项目工具链有实际用途。日志存在 Action 自身 `go.sum` 路径无法解析的缓存警告。当前 GTR 62 秒包含下载安装、重复缓存和真正测试，不能把它全部算作报告开销。建议给自有 Action 增加“复用已安装 CLI/工具链、关闭内部缓存”的输入；也可固定预编译 CLI 校验和直接调用，但需要保留失败报告、输出协议和退出码。
- **go mod tidy**：当前执行后不检查差异，会静默改变 CI 的待测依赖树。独立改为 `go mod tidy -diff`，或 tidy 后 `git diff --exit-code -- go.mod go.sum`。本地用临时 GOCACHE 运行 `go mod tidy -diff` 成功，当前 checkout 无需依赖修正。
- **两个轻量校验**：各 5–10 秒，没有必要为几百毫秒下载增加独立缓存。可并成一个 workflow 配置检查 job；actionlint 当前只覆盖 ci/release/publish-ghcr 三个文件，应覆盖全部工作流。`goreleaser check` 不需要全历史 checkout。
- **覆盖率产物**：保留 HTML、原始 profile 和失败证据。PR 在 GTR 与后续 shell 重复检查同一 85% 门槛，计算本身不足 1 秒；统一输出和门槛实现即可，不是性能重点。

### 2. Clock acceptance：144–194 秒

虽然名称仍是 Clock，实际包含移动端、编辑器、安全、搜索、天气和图标回归，不能按名称只对 clock 文件变化运行。

- 资源生成与 Go 二进制编译 21–29 秒；浏览器依赖安装 22–24 秒。
- 编辑器主入口 19–20 秒，并且末尾自动运行 `reliability.browser.cjs`；归档验收再次调用同一个入口时也会重复可靠性测试。
- 两次 hybrid search 各 7–8 秒，但 public/private 模式不同，应保留。
- 天气 12–15 秒，使用 Go 测试内的专用 Fiber app、stub provider；不是单纯启动生产二进制，不能直接用 `FLARE_BINARY` 替换。
- MDI clipboard 10–18 秒；巨大 HTML 的载入和真实 locator/clipboard 验证有成本。可减少浏览器实例、测量 page.setContent 的解析时间，保留 vendor 与 generated 两份验证。
- 其余独立验收多数 1–6 秒，scratch timezone 1–2 秒，不值得为了少量时间删除。

先优化准备阶段和归档重复测试，再考虑分成 2 个有隔离端口/配置目录的验收组。当前都是 `node script.cjs` 而非 Playwright Test runner，不能直接追加 `--shard`。分组会重复安装浏览器和下载二进制，需测净收益；不要把 20 个脚本各拆一 job。

### 3. Release preflight：主要瓶颈，5 个并行 job

总 runner 643–675 秒。归档 212–249 秒；amd64 镜像 70–87，arm64 99–117，armv6 119–122，armv7 115–121 秒。

**归档：**七个 GOOS/GOARCH/GOARM 在 Python for 循环中串行 `go build`。构建与检查步骤 128–169 秒。之前的工作区生成 12–16 秒，脚本又在 `git archive` 的临时快照生成一次。第二次生成必需：部分 editor/guide 资源故意被 Git 忽略，快照不会自动包含工作区生成结果。

建议将七平台构建拆成有界并行（先试 2 个 worker；与 runner 核数和内存匹配），或有限 matrix；不要默认七个独立 runner 最优。共享依赖与源快照，在测试前只生成一次可验证的生产资源。若保留生成文件一致性检查，需分别验证 tracked 输出与 ignored 输出，不能只删快照生成。

**镜像：**另外 4 个 job 又生成资源、编译四个 Linux 二进制，与七平台归档中的 Linux 构建重叠。当前每次 PR 至少 12 次生产目标编译（归档 7 + 镜像 4 + Clock 1），不计 Go 测试与 CodeQL。

复用同一运行的 Linux build artifact 可省每个镜像的资源生成 10–16 秒、编译 9–24 秒与 Go 安装 7–10 秒；但如果让镜像等待整个 249 秒归档 job，镜像才开始执行，会恶化最长路径。更好的依赖结构：资源准备 → 按目标构建并尽早上传二进制 → 归档检查和相应镜像并行消费。工件关联运行、源 SHA、目标架构、版本和校验和；不要用可回退 cache 当发布二进制来源。

**Docker/UPX：**样本 armv7 镜像日志显示 `apk add upx && upx -9 ...` 用 51.0 秒，整个 build 步骤 57 秒。COPY flare 在安装 upx 之前，二进制每次改变都会让安装工具和压缩同时失效；缓存不能消除变更二进制的压缩。

- 先安装 upx，再 COPY flare；将 tzdata 安装放在可复用的独立运行时基础层。
- 给 buildx 显式配置 `cache-from/cache-to type=gha`，scope 区分平台，采用 mode=max，保留中间构建阶段。当前只 setup-buildx，没有导入/导出跨运行的 layer cache。
- 若保留 UPX，尝试 `FROM --platform=$BUILDPLATFORM` 的原生 builder 压缩目标 ELF，逐架构验证旧 UPX 的支持，再做各目标容器启动与重启测试；运行目标架构容器仍需要 QEMU。
- 对 `-9`、较低压缩等级、不压缩进行实测，比较镜像压缩传输大小、启动耗时、峰值内存和 CI 耗时后决定。不能把 51 秒全部归因于 QEMU，也不能仅为提速改变发布格式。
- amd64 镜像无需安装 QEMU；其他平台限制注册范围。setup-qemu 的 binfmt 镜像缓存与 setup-buildx 的工具缓存已经生效，问题是应用 layer cache 缺失。
- `RUN ls -al` 两处是调试残留，可删以简化，但并非主要耗时。

归档验收又安装浏览器 24–28 秒，编辑器/legacy 验收 20–22 秒。这验证了“归档二进制”，有独立价值；改为针对打包错误的最小生产资源/编辑器 smoke，完整交互可靠性保留在 Clock。减少重复必须保留归档解压后可执行文件的验证。

全预检硬编码版本 0.6.6，之后版本会失真。参数化候选版本。跨平台完整预检可按 release/build/Docker/Go 或资源变化启用，纯文档跳过；Go 和公共模板变化仍需视为影响所有平台。减少执行范围属于验证策略变化，应保留 tag/手动完整预检。

### 4. Security Scan：108–119 秒

样本 A：拉 gosec 镜像 9 秒、宿主 setup-go 9 秒、宿主 go mod download 2 秒、扫描 86 秒、SARIF 上传 7 秒。

`securego/gosec@master` 是 Docker Action。日志 docker run 只挂载 workspace 等标准目录，没有挂载宿主 `/home/runner/go/pkg/mod` 与 `~/.cache/go-build`；宿主缓存不会直接进入扫描容器。宿主先准备 Go 与模块，不能为容器提供所期望的缓存收益。

优先改为固定版本/校验和的原生 gosec CLI，用项目工具链和有效 Go 缓存运行，并保留 SARIF。若继续 Docker Action，应删除无消费者的宿主 setup-go/download，或显式设计容器缓存挂载。扫描本身的语义依赖必须验证，不能只删初始化后假设等价。

push paths 未列 go.mod、go.sum、build、embed；PR 又无 paths，策略不一致。应覆盖依赖与生成资源入口。CodeQL 与 gosec 规则覆盖不同，不能仅因都是安全检查就删一个。保留每周扫描以覆盖规则/依赖漏洞变化。当前 `-no-fail` 说明它是 SARIF 报告，不是阻断门槛；若更换实现需保持或明确调整该行为。

### 5. CodeQL：102–113 秒

初始化约 14 秒，autobuild 35 秒，分析 37 秒。Go 普通构建缓存不能替代 CodeQL 带提取器的分析构建，不能直接复用普通二进制后删除 autobuild。可评估受支持的 Go 无构建分析模式、依赖缓存配置与分析覆盖差异，但要用官方支持矩阵及结果对比确认。单语言 matrix 可简化 YAML，对性能收益很小。

同样使用合理的变更过滤及 PR concurrency；保留 schedule。路径过滤应包含 .github/workflows、Go 依赖、生成器与公共资源。现有 CodeQL PR 分支范围缺少 `feat/search-*`，需与其余检查统一，而不是利用遗漏“省时间”。

### 6. Release：main 推送有无效发布准备

main 样本 build job 67 秒：Go 10、QEMU 7、模块缓存 2、生成+tidy+测试 41 秒，还执行 Docker Hub 登录；GoReleaser 因非 tag 跳过。真正发布 0.6.6 的 build 331 秒，其中 GoReleaser 260 秒；后续 GHCR 22 秒、dispatch 3 秒。

把 Release 限制到正式 tag；手动入口显式选择并验证 tag。目前从 main 手动运行同样不会发布。main 的质量回归交给 CI，删除这一轮无发布结果的准备，样本每次 main push 直接省 67 runner 秒，且减少不必要的 registry 登录。

正式 tag 测试和质量报告的 race 测试存在重叠，但标签事件没有运行主 CI 的 85% gate，独立质量报告 floor 又是 0，不能把 tag 测试和 gate 全删。可让发布依赖同一 SHA 的成功质量门槛，沿用可靠的 artifact/attempt 校验；这是发布依赖关系调整，需要确保不发布未验证二进制。GoReleaser before hook 又生成一次资源；如前置测试依赖资源，需要保留测试前的生成或从单一准备 job 获取。

### 7. Publish GHCR：22 秒，当前设计有效

crane 直接复制 Docker Hub 已发布多架构镜像，镜像复制验证 17 秒，没有重编译与 QEMU。保留 digest、commit、四平台验证和 latest 串行保护。工具下载不足 1 秒，无需为其新增缓存；无需改成第二次 Docker 构建。

### 8. Go quality reports：已有有效去重

0.6.6 tag：gate 6、reports 99、writeback 8 秒。Release 完成后的 dispatch：gate 8 秒，其余 job skipped，已验证复用生效。

当前同时支持 tag push、release published 和 dispatch；gate 仅复用已经完成成功且工件未过期的 tag 报告。不能将全部触发简单视为重复。若两个触发到达时 tag 报告仍在运行，仍有重复执行窗口；含 run_id 的 concurrency group 不会去重。可采用按源 SHA 的协调与重新检查，并保留手动强制刷新语义。不要直接套 `cancel-in-progress: true` 到发布/写回流程。

此 workflow 没有先生成生产资源，且报告没有 `cover_pkg: ./...`；与 PR 85% 全包覆盖率口径不同。改为复用它作为发布 gate 前必须统一资源准备和覆盖范围。现有报告是独立 baseline，不应当作 PR gate 的等价证据。

## 缓存整改方案

### 已证明的问题

1. setup-go v6 当前默认依赖文件是 **go.mod**（需以实际版本源码为准）；GTR 使用显式 go.sum。因此样本中外层缓存键结尾 `d556eb...` 与 GTR 的 `ca8893...` 并不一致。所有项目 setup-go 应显式指定 `cache-dependency-path: go.sum` 或统一自管键，避免版本默认值变化。
2. 外层缓存精确命中 7,515 B，结束时 `Cache hit occurred ... not saving cache`。这是无有效编译/模块内容的缓存，hit 不等于有收益。fmt 这种轻任务参与同一 key 保存，存在抢先保存空缓存的路径；**本次没有追溯到最初创建者，fmt 是机制推断，非已证明的历史创建者**。
3. 手动模块缓存恢复 148,325,108 B；GTR 又恢复 292,775,705 B，出现大量 tar `Cannot open: File exists`。Go 模块文件只读，重复覆盖会失败。这是日志中的实际错误，即使 job 最终 success 也不能算缓存健康。
4. 两个报告 Action 自身的 go.sum 路径无法解析，导致工具缓存恢复警告，且仍安装第二套 Go 工具链。
5. setup-go 基于依赖的精确 key 是不可变快照：即使去除空缓存，之后添加的 race、跨平台编译结果也不会自动补入原 key。不能认为相同依赖就能持续更新编译缓存。

### 推荐逐步实施

- 最小修复：fmt `cache:false`；项目显式 go.sum；删除 test/Release 的手动模块缓存，并**同时**解决 GTR 内部二次 restore（修改自有 Action、隔离工具目录或统一缓存控制）。仅删除那两个手动步骤仍不能根治多次 setup-go restore。
- 用新 namespace 代替已经无效的旧 key；不用删除整个仓库缓存。只配置一个清晰的保存者，先下载模块、编译/测试成功后再保存。不同 job 同时开始时无法靠同一 key 即时共享成果；共享本轮产物用 artifact 或明确 needs。
- 进一步分离模块缓存与编译缓存：模块 cache 按 OS/runner arch + go.sum，依赖稳定可复用；GOCACHE 按 Go 版本、runner image、任务族（race、native build、cross build），key 包含配置及源指纹，restore prefix 仅回退同工具链/任务族。Go 自身验证内容哈希，但不应混用不兼容环境。只在完整 key 未命中时由成功生产者 save，设置容量与保留策略，避免每次唯一 key 无限堆积。
- 可信 main build/test 负责维护可复用基线；PR 可以读默认分支缓存，但 PR 保存的 merge-ref 缓存不能指望反向供 main 或其他 PR 使用。不要为提高命中率把不可信发布二进制放入宽泛 restore key。
- npm 下载缓存已经精确按 lockfile 命中，约 4 MB，保留；它不缓存 node_modules，也不缓存 Chromium，npm ci 仍需运行。无需缓存 node_modules。
- Playwright 浏览器缓存只做 A/B 实验：key 包含 OS/arch/Playwright 精确版本，系统库仍需安装。官方明确提醒恢复浏览器可能与下载同样耗时；不能把 22–28 秒安装全部算成可节省时间。当前全部 headless 默认 Chromium 可评估 `install --with-deps --only-shell chromium`，先确认没有显式 channel/executablePath 需求。预置 Playwright 镜像也是选项，但需把镜像拉取及 Docker smoke 的环境差异算入。
- buildx layer cache 按目标平台分 scope；release 二进制/包用 artifact，缓存不替代 provenance。UPX 对新二进制仍需重跑。

## 执行顺序与验收

**第一批：保持验证范围，修掉无效工作。**修复缓存所有权/键、关闭 fmt 缓存、移除 main Release、PR 工作流加 `concurrency`，固定工具版本、依赖只读检查、合并轻量校验、扩展 actionlint 范围。CI/Clock/preflight/CodeQL/gosec 可使用 `${{ github.workflow }}-${{ github.event.pull_request.number || github.ref }}`，仅对 PR 设置取消旧运行；发布和报告写回保留串行完整性。

**第二批：改变构建依赖图。**七目标有界并行、生产资源单一准备、按目标尽早共享 Linux 二进制、Docker 分层/原生 UPX 评估、gosec 原生 CLI。不要为了去重增加所有镜像对整个归档 job 的串行依赖。

**第三批：减少执行范围。**文档与纯报告变化跳过重构建；保留始终回报结论的轻 gate，使用 job 条件而非让 required workflow 因 paths 被整个跳过而一直 pending。公共 Go/模板/依赖变化仍跑完整相关验收。预检中编辑器全交互缩成打包 smoke，完整功能回归集中在 Clock。PR 与合并后 main 验证 source SHA/merge tree 不同，不能无条件用前者替代后者。

对每批收集至少 5 次冷/热运行及小改动：比较最长路径、各 job 合计、缓存恢复/保存成本、下载/编译耗时、缓存体积与命中类型。新增依赖、Go 升级、ARM v6/v7、失败证据和旧 PR 取消都要覆盖。通过标准：无 tar 覆盖错误，无缓存路径警告，真正重任务产出可用缓存，race/85% gate/跨平台/归档/容器与 SARIF 证据仍有效。优化前后数据必须按相同代码与 runner 条件比较。

# 跳转路径 CPU 与分配分析：2026-10-25

> 历史实验记录：本文的构建标签、默认框架及源码路径描述对应测量当时的实验阶段。当前默认已切换为 64 KiB Fiber；完整记录和复现边界见 [性能总览](../docs/performance.md)。原始数字与当时结论保持不变。

保留 **64 KiB** 读取缓冲，已移除书签缓存命中时多余的工作目录解析。正式独立服务测量中，64 KiB 跳转吞吐提高 **32.1% / 38.9%**，每请求 CPU 时间下降 **15.3% / 17.6%**；采样峰值 RSS 的中位数变化为 **+0.21 / −0.10 MiB**，基本持平。改动没有新增缓存、索引或对象池。这里不能声称 RSS 明显下降，也不保证所有环境中 RSS 严格零增长。

## 找到了什么

默认跳转目标在应用列表的第一条命中，但旧路径每次仍调用 `LoadFavoriteBookmarks()`：独占书签锁、解析工作目录、检查文件、读取已缓存的原始 YAML 字节，再完整解析八条应用记录。主要问题不是 302 响应构造本身。

独立服务端 CPU profile 显示，优化前 `getConfigPath → os.Getwd` 占总 CPU 样本约 **20.6%–23.6%**；YAML 解码占采样累计分配字节的 **93.5%–94.4%**。路径解析位于书签锁内，额外文件系统调用也延长了串行区间。优化后，暖缓存阶段的 `Getwd` 热点不再出现在采样中；完整 YAML 解析仍然保留。

现有基线用 `os.Chdir` 切换到临时数据目录，却没有同步 `PWD`。这会让 `os.Getwd` 在验证环境变量之后走更慢的路径，放大本机测量中的开销。本次没有改动原基线环境；另用 `PWD` 匹配和不匹配两种微基准核对。不能把这里的完整收益直接套用于生产环境。

## 为什么 64 KiB 曾比 8 KiB 慢

- 读取缓冲按连接获取并复用。池未命中时 64 KiB 分配更大，连接池和 GC 状态会影响成本；它不会每个请求都整块重建或扫描。
- 默认客户端池中，优化前 reader 分配约占采样 `alloc_space` 的 **0.08%（8 KiB）/ 0.64%（64 KiB）**；优化后为 **0.25% / 1.62%**。8 条空闲连接池的这些 profile 未采样到 reader 分配，不能将其解读为精确的零分配。
- 正式测量中，64 KiB 对 8 KiB 的额外分配字节在默认池约 **0.21–0.35 KiB/请求**，在 8 条池接近零。CPU profile 中 reader 获取未形成可见热点。较大缓冲有成本，但这些证据不足以把上一轮全部 CPU 差距归因于它。
- 本轮优化前，64 KiB 的吞吐比 8 KiB 低 **2.2% / 6.1%**；优化后差距缩至 **0.9% / 0.2%**。两种尺寸都受益，说明移除的是共有热路径的浪费，不能据此证明上一轮差距只有一个原因。

## 实际改动

只调整 `config/data/bookmark.go` 的读取流程：每次仍以相对文件名检查文件是否存在；仅在需要初始化文件或原始字节缓存未命中时，才调用 `getConfigPath` 解析绝对路径。锁、完整 YAML 校验、保存后的缓存失效和跳转白名单逻辑保持原样。

改动位于 Echo 与 Fiber 共用的书签读取层，两种构建均采用；本次性能比较只覆盖 Fiber 跳转。未加入已解析 YAML 缓存、URL 索引或新的池，也未调整 64 KiB、Immutable、GC 参数、响应内容或客户端连接池设置。

## 无 profile 的正式对照

Apple M5 / macOS 26.5.1 / ARM64、Go 1.27.3；离线、关闭登录与请求日志、默认数据、并发 8、GOMAXPROCS=4，GOGC/GOMEMLIMIT 未设置。四个目标分别为旧/新实现的 8 KiB 与 64 KiB，均使用同一个 Echo 构建的外部客户端。每次启动全新的原生服务进程，1000 请求预热后执行 100000 请求，共 8 轮；每个目标在四个执行位置各出现两次。两组共 64 条记录，响应均为预期的 HTTP 302、空响应体与相同 Location，实际缓冲全部核对正确。

### 64 KiB 优化前后

| 客户端空闲池 | QPS 变化 | CPU 变化 | 分配次数变化 | 分配字节变化 | RSS 差（MiB） |
| --- | ---: | ---: | ---: | ---: | ---: |
| 默认 2 条 | +32.1% | -15.3% | -1.7% | -2.8% | +0.211 |
| 8 条 | +38.9% | -17.6% | -1.7% | -3.8% | -0.102 |

CPU 为目标进程用户态与内核态时间之和除以请求数；分配来自目标进程运行时计数。RSS 每 50 ms 采样，包含代码页、运行时和堆，可能漏掉短暂尖峰。控制接口快照的少量固定开销也会进入计数。客户端运行在独立进程，未混入这些服务端资源数据。

RSS 的两组变化方向相反，绝对差小于 0.22 MiB；默认池旧 64 KiB 的逐轮范围约 27.25–29.05 MiB，新版本约 27.55–28.09 MiB。因此结论是 **RSS 基本持平、单请求分配减少，速度没有靠新增常驻缓存换取**。分配字节减少不能直接推导 RSS 必须下降；也不能以本轮数据保证严格的内存上界。

## 工作目录微基准

同一个 `BenchmarkLoadFavoriteBookmarks` 测试源码，旧实现通过 Go overlay 还原；前后顺序交替运行四轮，单子基准计时 1 秒、GOMAXPROCS=4。每轮初始化默认八条应用并预热原始字节缓存，初始化不计时。这是单次书签加载调用的微基准，不是 HTTP 资源指标。

| PWD 状态 | 版本 | ns/调用 | B/调用 | allocs/调用 |
| --- | --- | ---: | ---: | ---: |
| 匹配工作目录 | 优化前 | 19740 | 19776 | 351 |
| 匹配工作目录 | 优化后 | 16616 | 18992 | 346 |
| 不匹配工作目录 | 优化前 | 29528 | 19888 | 352 |
| 不匹配工作目录 | 优化后 | 17442 | 18992 | 346 |

PWD 匹配时调用耗时下降约 **15.8%**，不匹配时下降约 **40.9%**。这支持路径优化在常见目录环境中也有收益，同时确认原基线会放大它。微基准存在不同进程与调度噪声，不能把这些百分比直接当作 HTTP QPS 增幅。

## Profile 证据与限制

每个尺寸和版本分别在两种客户端池下诊断：1000 次预热，下载同进程的 heap 前快照，启动 15 秒 CPU 采样并发送 200000 次跳转请求，再下载 heap 后快照。CPU 与 heap 均来自独立目标进程；没有更改 Go 默认采样率。CPU 固定窗口与负载并非严格等长，profile 期间的 QPS 和 RSS 不用作正式收益。

## 回归与复现

新回归覆盖应用与普通书签集合的缓存命中、删除后初始化、保存失效、错误 PWD 下读到当前目录数据，以及无效 YAML/非 URL 字段错误仍被完整校验。原有 Fiber 原生路由、64 KiB 容量与 HTTP 431、TLS Cookie 登录/登出测试继续通过。控制口另有 heap 二进制响应测试。

以下全部通过：

```sh
go test ./...
go vet ./...
go test -tags fiber ./...
go vet -tags fiber ./...
go test -race -tags fiber ./config/data ./internal/server ./tools/baseline
```

基线 profile 控制接口只存在于 `tools/baseline -serve` 的独立回环端口，不在应用服务中开放。原 `-cpuprofile`/`-memprofile` 仍描述单进程基线；本次使用新独立控制口避免混入客户端。

正式对照命令（各版本二进制在同轮构建，原源码与 overlay 已保留）：

```sh
python3 scripts/analyze-redirect.py \
  --output .benchmark/redirect-analysis-2026-10-25/measurements \
  --target before_8kib=.benchmark/redirect-analysis-2026-10-25/before-8kib \
  --target before_64kib=.benchmark/redirect-analysis-2026-10-25/before-64kib \
  --target after_8kib=.benchmark/redirect-analysis-2026-10-25/after-8kib \
  --target after_64kib=.benchmark/redirect-analysis-2026-10-25/after-64kib \
  --client .benchmark/fiber-64kib-buffer/echo-baseline \
  --rounds 8 --resource-requests 100000 --resource-warmup 1000 \
  --concurrency 8 --gomaxprocs 4 --pools 0 8
```

独立诊断使用同一脚本，换一个输出目录并添加 `--profiles-only --profile-seconds 15 --profile-requests 200000`，`--target` 选需要诊断的二进制。测试包微基准可用 `GOMAXPROCS=4 go test ./config/data -run '^$' -bench '^BenchmarkLoadFavoriteBookmarks$' -benchmem`。更完整的参数说明见 [基线文档](../docs/baseline-metrics.md)。

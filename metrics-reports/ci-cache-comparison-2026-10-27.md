工作流耗时取最早任务开始至最后任务结束，包含任务间调度等待；累计任务时间为各任务运行时间之和，不等于 GitHub 实际计费分钟。五个工作流的 rerun 请求依次发出，不用请求发出时间比较整体墙钟时间。

## 缓存命中与有效性

- Go 编译缓存：冷轮 0/13，热轮 13/13，热轮全部为请求键精确命中。
- 模块缓存：冷轮首批 6 次未命中，后续 7 个目标任务共享命中；热轮 13/13 精确命中。冷轮内的共享符合源准备任务先完成再展开矩阵的依赖图。
- 四个容器平台：冷轮 UPX 层全部执行，热轮全部 `CACHED`。缓存导入后没有继续执行压缩。
- 七个平台冷、热轮二进制 SHA256 全部相同。验证记录中的实际构建时间不同；候选二进制使用同一源提交日期，证明临时路径和当前时间已不再破坏同源构建复用。归档自身仍带实际生成时间，不要求 tar.gz 哈希一致。
- 热轮没有 Go 缓存缺失、`Cannot open: File exists` 或恢复失败记录。命中没有替代任何测试执行。

## 验证期间修复的问题

1. 临时源目录使 Go 主包缓存失效：生成和候选构建增加 `-trimpath`，候选增加 `-buildvcs=false`。
2. 当前构建时间使二进制变化、UPX 层始终失效：候选版本嵌入源提交日期，单独记录实际构建时间；正式发布日期逻辑保留。
3. `-trimpath` 不保留原链接参数，旧元数据检查误报：直接验证归档二进制内的提交与版本，并保留 Go 平台、ARM 版本、CGO、归档校验和及来源校验。缺失嵌入元数据的负例仍须失败。
4. 早期诊断轮旧下载器在成功日志后停留近三分钟：统一使用仓库已有固定 SHA 的 download-artifact v8.0.1。旧轮聚合下载步骤 182 秒；本次冷、热轮均为 2 秒。这是诊断观察，不将单次网络差异完全归因于动作升级。

## 保留的校验与后续建议

两轮都执行 race、`-count=1`、全包覆盖率和 85% 门槛，实际覆盖率均为 86.2%；七目标归档、四平台运行验收、归档二进制浏览器验收、Clock 全部浏览器测试、静态检查、CodeQL 和 gosec 均通过。正式 Release 的标签/提交校验、GoReleaser 检查、GHCR 校验及报告流程保留；此次不执行发布。

热轮发布预检的归档聚合任务仍为 65 秒（冷轮 64 秒），主要是浏览器依赖准备和实际验收；这些步骤用于保持现有验收覆盖。四路并行仍有第二批矩阵调度成本；如后续需要进一步压缩墙钟时间，可先测量提高并发对仓库其他工作流的排队影响。不要仅凭单次结果扩大并发或缓存浏览器系统依赖。

继续观察兼容前缀恢复、缓存总量与淘汰情况。每次改变 Go 版本、依赖、编译参数或缓存路径后，应重新执行这种同提交冷/热配对测量。不要将“有 cache hit 日志”当作节省工作已得到证明；同时检查编译耗时、压缩层 `CACHED` 和产物一致性。
